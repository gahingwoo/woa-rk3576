# Radxa ROCK 4D 的 Wi-Fi 和蓝牙（USB 接口的 AIC8800D80）

[English](aic8800.md) | 简体中文

状态（2026-11-25）：驱动 `drivers/net/aic8800usb`（分支 `aic8800-usb`）能下载固件、扫描、用自带的 supplicant 加入一个 WPA2-PSK 网络，并在这条链路上给 Windows 提供一个网络适配器（NetAdapterCx，以太网帧）。**这里的东西都还没在板子上跑过。** 协议代码在主机上对着模拟芯片和模拟 AP 通过了测试（`tools/aictest`，包括端到端的 DHCP、ARP 和 ping），CI 里用真实固件文件跑了下载流程，每个消息 ID 和参数偏移都在编译期对照了 AICSemi 自己的头文件。这是以太网式模式：适配器看起来像有线网卡。Windows 自己的 Wi-Fi（网络列表、任务栏、它自己的 supplicant）是 WiFiCx 模式，在分支 `aic8800-wificx` 上，同一个驱动配 `aic8800wifi.inf`：见 [wificx.zh-CN.md](wificx.zh-CN.md)。

## 硬件

量产版 ROCK 4D 用的是 AICSemi AIC8800D80，Wi-Fi 6 加蓝牙 5.4 的二合一芯片，走 USB（CNX Software 记的模块型号是 FCU760K）。Radxa Dragon Q6A 用的是同一颗芯片。edk2-rk3576 的 ROCK 4D 平台代码在启动时就给它上电（GPIO2 PC7 `vcc_3v3_wifi`，GPIO2 PD1 rfkill），所以不需要 Windows 做什么，它就会出现在 DWC3 主机上。

这颗芯片在 USB 上有两种身份：

| USB ID | 何时 | 接口 |
|---|---|---|
| `VID_A69C&PID_8D80` | 上电时：ROM 加载器 | 一个厂商接口（FF/FF/FF），bulk IN 和 OUT 各一 |
| `VID_A69C&PID_8D81` | 固件下载之后 | MI_00 和 MI_01：蓝牙 HCI（E0/01/01）；MI_02：WLAN（FF/FF/FF），bulk IN、OUT 各两个 |

## 现有的 Windows 驱动与 23H2

Mario Bălănică 的 `aicwlan`（worproject/dldserv-mirror 的发布附件 `aicwlan_arm64_0935761.zip`）是这颗芯片的 WiFiCx 驱动。它是没有许可证的二进制，可以用，但这里不能复制、修改或分发。它的 INF 只在 Windows 11 24H2 及以后安装（`NTARM64.10.0...26100`），而 24H2 在 RK3576 上起不来（ARMv8.0，没有 LSE 原子指令）。二进制本身是否需要 24H2，是通过读它的 WDF 绑定信息查的（那个 zip 里的 `aicwlan.sys`，配合包里的 `aicwlan.pdb` 符号）：

| | aicwlan.sys 绑定的 | Windows 11 22621（22H2/23H2）提供的 |
|---|---|---|
| KMDF | 1.33，`WdfMinimumVersionRequired` 33 | 1.33 |
| NetAdapterCx | 2.2（124 个函数） | 2.3（[版本表](https://learn.microsoft.com/en-us/windows-hardware/drivers/netcx/netadaptercx-version-overview)）；22H2 上 WiFiCx 驱动本来就必须绑 2.2 |
| WiFiCx | **1.2**（40 个函数），`WifiMinimumVersionRequired` **2** | **1.0** |
| ntoskrnl、HAL、WppRecorder | 23 个普通导入（`ExAllocatePool2`、`Zw*File`、`KeWaitForSingleObject` 等） | 全都有（`ExAllocatePool2` 从 2004 起就有） |

决定性的是 WiFiCx 这一行。22621.2428 镜像里的 `wificx.sys`（10.0.22621.2215）把自己的类库注册为 1.0 版（从微软公开符号里的 `WdfClassLibraryInfo` 读出）。微软的 [WiFiCx 版本说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/netcx/building-a-wificx-driver-for-multiple-versions-of-windows) 写明：21H2 和 22H2 只支持 WiFiCx 1.0，1.1 和 1.2 从 Insider 25330（24H2 那条线）开始；1.1/1.2 的驱动只有在用 `WIFI_MINIMUM_VERSION_REQUIRED=0` 编译时才能跑在 1.0 上。aicwlan 编译时用的是 2。所以把 INF 的版本下限改低以后，它能在 23H2 上装上，但驱动启动时类扩展的绑定应当失败（预计：代码 10 或 31，事件日志里有 WiFiCx 版本不匹配）。要在 23H2 上用它，只有两条路：作者把最低版本设为 0 重新编译（并给 1.1/1.2 的调用加运行时检查），或者我们自己写驱动。本仓库不修补这个二进制。

## 在 23H2 上私下试 aicwlan

代价小，能验证上面的分析，只给板子的主人自己用：改过的 INF 只留在板子上，绝不提交、发布或放进镜像。

1. ROCK 4D，Windows 11 23H2（22631），开测试签名（`bcdedit /set testsigning on`，和其他板子一样）。确认加载器出现：`pnputil /enum-devices /connected | findstr A69C` 能看到 `USB\VID_A69C&PID_8D80`。
2. 把 `aicwlan_arm64_0935761.zip` 解压到板子上的一个文件夹。在 `aicwlan.inf` 里把两处 `NTARM64.10.0...26100` 改成 `NTARM64.10.0...22621`（`[Manufacturer]` 那一行和型号段名），别的都不动。
3. 生成目录文件并用本地证书签名（在任何装了 WDK 的 PC 上）：`inf2cat /driver:<文件夹> /os:10_NI_ARM64`，然后 `signtool sign /fd sha256 /f test.pfx /p <密码> <文件夹>\aicwlan.cat`。`.sys` 保留 Mario 自己的测试签名。在板子上把 `test.cer` 导入 Root 和 TrustedPublisher（`certutil -addstore -f`）。
4. 只暂存，不热装：`pnputil /add-driver <文件夹>\aicwlan.inf`，然后重启 Windows。
5. 读取：设备管理器里加载器设备的状态和问题代码；`Get-WinEvent -LogName System -MaxEvents 50 | ? ProviderName -match 'wdf|kernel-pnp|aicwlan'`；绑定过程看 `C:\Windows\INF\setupapi.dev.log`。预期：加载器设备装上 aicwlan，固件也许会启动，然后驱动因 WiFiCx 版本错误启动失败。通过（意外情况）：出现 Wi-Fi 适配器，`netsh wlan show networks` 能列出网络。
6. 试完删掉：`pnputil /enum-drivers` 找到它的 `oemNN.inf`，`pnputil /delete-driver oemNN.inf /uninstall`，重启。

## USB 协议

全部来自 AICSemi 的驱动（文件出处见 `aic_proto.h`）：

- **包。** 每次 bulk 传输里有一个或多个包，开头是 `u16 len`（12 位）、`u8 type`、`u8 0`。主机到设备：控制消息 type 为 0x11，接一个占位字，再接 LMAC 头（`id`、目标任务、源任务 = 100、`param_len`）和参数；数据帧 type 为 0x01，接 28 字节的主机描述符和以太网载荷，按 4 字节补齐，如果传输长度正好落在 512 字节边界上就再多补一个字节。设备到主机：type 带 0x10 位的是消息（0x11 是确认或通知，E2A 头里有一个 pattern 字；0x12 是 TX 确认；0x13 是固件控制台文本）；其余是数据包：60 字节的 RX 头（长度、解密状态、VIF/站点索引）加 802.11 帧。
- **消息 ID** 是 `task << 10 | index`（MM 0、DBG 1、SCANU 4、ME 5、SM 6）。每个请求都指定驱动要等的确认消息。
- **固件下载**（ROM 加载器，DBG 任务）：在 0x40500000 读芯片 ID；按补丁表 `AICBT_PINF_T` 段给的地址（当前文件是 0x201940、0x1E0000、0x20B43C）用 1024 字节的 `DBG_MEM_BLOCK_WRITE` 写入 adid、patch 和 ext 文件；写补丁表里的每一个地址/值对（当前这份是 140 个），其中 `AICBT_MODE_T` 段换成蓝牙设置；在 0x120000 写 `fmacfw`；做 "patch config"（通过镜像里 0x120198/0x1201A0/0x1201A4 处的指针找到配置基址和补丁块，写 `PTCH` 魔数和三项设置）；在 0x120000 发 `DBG_START_APP`。芯片离开总线，再以 PID_8D81 回来。
- **运行时初始化**：`MM_SET_STACK_START`、`MM_GET_FW_VERSION`、`MM_SET_RF_CALIB`、`MM_GET_MAC_ADDR`、`MM_RESET`、`MM_VERSION`、`ME_CONFIG`（目前只开 HT20）、`ME_CHAN_CONFIG`、`MM_START`、`MM_ADD_IF`（station）。
- **扫描**：`SCANU_START`（2.4 GHz 全部信道加 25 个 5 GHz 信道，一个通配 SSID）；每个 beacon 或 probe response 以 `SCANU_RESULT_IND` 送上来，结束时是 `SCANU_START_CFM`。
- **加入网络**：`SM_CONNECT` 带上 RSN IE、`CONTROL_PORT_HOST` 和 `WPA_WPA2_IN_USE`；`SM_CONNECT_IND` 给出 AP 的站点索引。固件自己不跑 WPA2：4 次握手以 EAPOL 数据帧送上来，主机像 Linux 上的 wpa_supplicant 那样应答，然后用 `MM_KEY_ADD` 装密钥，用 `ME_SET_CONTROL_PORT` 打开端口。
- **数据**：TX 交给固件以太网载荷和地址、ethertype；RX 交给主机已解密的 802.11 帧，主机把它变成以太网帧（去掉 802.11 头、安全头和 LLC/SNAP 头；拆开 A-MSDU）。

## 驱动设计与阶段

和 `bcmwlsdio`（泰山派 3M 的 Broadcom 驱动）同样的结构：一个不依赖 Windows 和 libc 的可移植核心（`aic_*.c`，CI 里用 `-ffreestanding -nostdinc` 编译），外面一层薄薄的 KMDF 文件（`driver.c`、`usb.c`、`files.c`），一个 `Stage` 设置让每次上板只测一步，再加一个带模拟芯片的主机测试（`tools/aictest`）。

```
  tcpip / NDIS（系统自带）                       （WiFiCx 模式：wificx.zh-CN.md）
  NetAdapterCx 2.1：一个 TX 队列、一个 RX 队列
  -------------------------------------------------
  aic8800usb.sys（KMDF）：服务 aic8800ldr（加载器，System 类），
                          服务 aic8800usb（运行时，Net 类）
    driver.c     PnP、执行各阶段的工作线程、注册表记录
    netadapter.c 适配器：TX 收集分片并异步写 USB、填 RX 环、链路状态
    usb.c        管道、连续读取进环形缓冲、bulk OUT
    files.c      固件文件
    -- 可移植核心 --
    aic_core.c  分帧、命令/确认、接收分发
    aic_fw.c    芯片 ID、补丁表、下载、启动
    aic_wlan.c  运行时初始化、扫描、加入、密钥、通知
    aic_data.c  以太网与固件数据帧互转、A-MSDU
    aic_wpa.c   WPA2-PSK supplicant（4 次握手和组密钥握手）
    aic_crypto.c SHA-1、HMAC、PBKDF2、PRF、AES-128、密钥封装
  -------------------------------------------------
  usbccgp（PID_8D81）/ usbhub3 / DWC3 xHCI（系统自带）
```

为什么不直接上 WiFiCx：要实现和 Broadcom 那边一样的 WDI 命令与任务集，而且 23H2 只有 WiFiCx 1.0。Windows Wi-Fi 接口以下的部分（下载、初始化、扫描、加入、密钥、数据转换）在三种模型里都一样，所以先在一个以太网式的适配器下把它做出来并测好。

**适配器**（阶段 4）。运行时实例像 `dwc_eqos` 一样是 NetAdapterCx 客户端：介质 802.3，MTU 1500，MAC 来自模块的 `MM_GET_MAC_ADDR`（固件初始化放在 PrepareHardware 里做，这样适配器启动时就知道地址），Wi-Fi 链路连着时向 Windows 报告链路已连接。
- TX：把每个包的分片收集成一个以太网帧，用 `aic_build_tx` 在 32 个预先分配好的 USB 写请求之一里生成固件的数据帧，在数据管道上异步发送；复制完包就算完成。32 个都在途时队列停下，等某个完成后再向 NetAdapterCx 要包：这就是 TX 流控（还没用固件的 credit 通知）。
- RX：核心的接收路径在工作线程上运行；它产生的每个以太网帧进入 `aic_frameq`（64 帧），RX 队列的 advance 把它们复制进系统管理的缓冲区。
- 还没有 A-MPDU 重排：固件送上来的 block-ack 帧可能乱序（`flags_need_reord`），TCP 能应付，代价是一些吞吐量。

同一个二进制以两个服务绑定两种 USB 身份：加载器用 `aic8800ldr`（`aic8800ldr.inf`，System 类），运行时用 `aic8800usb`（`aic8800usb.inf`，Net 类）。加载器实例下载完固件后在一个易失键（`Parameters\Boot`）里记下 `FirmwareLoaded`；运行时实例如果找不到这条记录（固件是热重启时遗留下来还在跑的），就发重启类型的 `DBG_START_APP` 让芯片回到加载器，和 AICSemi 的 Linux 驱动一样，每次开机最多两次。

| 阶段 | 加载器（PID_8D80） | 运行时（PID_8D81 MI_02） |
|---|---|---|
| 0 | 选配置、列管道、记录 USB 身份和速度；不发任何东西 | 同左 |
| 1 | 再加：芯片 ID、下载并启动固件 | 再加：通过固件读芯片 ID |
| 2 | （同 1） | 再加：初始化、MAC、固件版本、station VIF、扫描写入 `ScanResults` |
| 3 | （同 1） | 再加：用 WPA2-PSK 加入 `Ssid`、装密钥、开端口；保持连接（组密钥更新、断线重连） |
| 4 | （同 1） | 再加：适配器收发流量，并向 Windows 报告链路状态 |

阶段 4 以下适配器也存在，但保持断开，这样每一步都能在没有 Windows 流量干扰的情况下测试。

## 注册表值

设置放在服务键 `HKLM\SYSTEM\CurrentControlSet\Services\aic8800usb\Parameters`（两个服务共用一处）：`Stage`、`Ssid`、`Passphrase`（第一次使用后换成 REG_BINARY 的 `Pmk`）、`FirmwareDir`、`ScanTimeoutMs`、`ConnectTimeoutMs`。用 `aic-bringup.ps1` 写入；`-Connect -Ssid <名字>` 会不回显地询问密码、设为阶段 4，并把这个键限制为只有 SYSTEM 和 Administrators 能访问（里面存着 PMK）。驱动从不记录或输出密码和 PMK。

记录写在各实例的 Device Parameters 下（`aic-bringup.ps1 -Status` 会打印）：

| 值 | 含义 |
|---|---|
| `LastStep`、`PrevStep`、`StepSeq` | 工作线程走到哪一步或停在哪一步；每步都刷盘 |
| `OpenStatus`、`UsbVid`、`UsbPid`、`UsbInterface`、`UsbHighSpeed`、`UsbBulkIn`、`UsbBulkOut`、`UsbOutMaxPacket` | 阶段 0 |
| `ChipWord`、`ChipRev`（3 = U02，7 = U03）、`ChipSubRev`、`ChipIsH`、`ChipMcu` | 芯片 ID |
| `FwFileStatus` | 读不到固件文件时的 NTSTATUS |
| `PatchSections`、`PatchWrites`、`PatchVersion`、`FwVersionWord`、`FwState` | 下载（成功时为 `started`） |
| `FwVersion`、`MacAddress`、`Is5gSupported`、`LmacVersion`、`FwFeatures` | 运行时初始化 |
| `ScanResults`（每行 SSID、BSSID、MHz、dBm、安全类型）、`ScanCount`、`ScanStatus` | 扫描 |
| `ConnectStatus`（802.11 状态码）、`HandshakeMsg`（处理到的最后一条 EAPOL 消息，4 = 完成）、`LinkFreq`、`LinkBssid`、`LinkState`（3 = 已连接）、`Reconnects`、`DisconnectReason` | 加入网络 |
| `TxMsg`、`RxMsg`、`RxInd`、`RxData`、`RxDataDropped`、`RxEapol`、`TxEapol`、`TxData`、`RxPrint`、`RxErrors`、`RxUnknown`、`LastUnknownMsg`、`FwPanic`、`MicFailures` | 核心计数 |
| `UsbSends`、`UsbSendErrors`、`UsbLastSendStatus`、`UsbRingDrops`、`UsbReaderErrors` | USB 计数 |
| `AdapterStartStatus`、`NetLinkReported`、`NetTxFrames`、`NetTxDrops`、`NetTxErrors`、`NetRxFrames`、`NetRxDrops` | 网络适配器 |
| `LastError` | 核心最近一次的错误文本 |

## 板上测试计划

ROCK 4D，Windows 11 23H2，开测试签名，用以太网远程访问。按[驱动的 README](../../drivers/net/aic8800usb/README.md) 安装：导入 `signer.cer`，运行 `install-firmware.ps1`，对两个 INF 都执行 `pnputil /add-driver`（只暂存），用 `aic-bringup.ps1` 设阶段，重启。每次重启后运行 `aic-bringup.ps1 -Status`，并保留固件启动的串口日志。aicwlan 的私下试验和本驱动不要同时装（两者都绑定 `PID_8D80`）；装一个之前先删掉另一个。

1. **阶段 0。** 通过：加载器设备显示为 "AIC8800D80 USB Wi-Fi (firmware loader)"，状态正常，`OpenStatus` 0，`UsbPid` 0x8D80，`UsbBulkIn` 至少 1，`UsbBulkOut` 至少 1，`UsbHighSpeed` 1。
2. **阶段 1。** 通过：加载器上 `ChipRev` 为 3 或 7，`FwState` 为 `started`，`PatchWrites` 140，`PatchVersion` 写着补丁表的构建信息，`FwVersionWord` 0x06090101；随后出现新设备 `PID_8D81&MI_02`，即网络适配器 "AIC8800D80 USB Wi-Fi"（未连接），`AdapterStartStatus` 0，`UsbBulkIn` 2，`UsbBulkOut` 2，`LastStep` 为 "runtime: identify"，`ChipRev` 相同。蓝牙 MI_00 出现为蓝牙无线电（见[蓝牙](#蓝牙)）。要记下的失败情形：`FwFileStatus`（文件缺失）、`LastError` 为 "no confirm for message 0x0400"（加载器不应答：端点选择或分帧有问题）、芯片一直不以 8D81 回来。
3. **阶段 2。** 通过：`FwVersion` 是真实的字符串，`MacAddress` 是模块的地址（和 Armbian 的 `ip link` 对照），`ScanCount` > 0，家里的网络出现在 `ScanResults` 里且 RSSI 合理；重复 3 次开机。在同一位置和 Armbian 的 `iw dev wlan0 scan` 对比。
4. **阶段 3。** `aic-bringup.ps1 -Connect -Ssid <家里的网络> -Stage 3`（在提示处输入密码）。通过：`LinkState` 3，`HandshakeMsg` 4，`ConnectStatus` 0，`MicFailures` 0，相隔一分钟的两次 `-Status` 之间 `RxData` 在增长（局域网广播解密后送上来了），路由器的客户端列表里有模块的 MAC；30 分钟后仍然连着（大多数路由器会做一次组密钥更新），路由器重启后能自己连回来（`Reconnects`）。冷启动 n = 5 次，必须全部通过。密码错误时必须得到 `HandshakeMsg` 2，`LastError` 为 "4-way handshake did not complete"。
5. **阶段 4。** `aic-bringup.ps1 -Stage 4`，重启；桌面出来后拔掉网线（或把有线网卡的跃点数调高），让流量必须走 Wi-Fi。依次通过：
   - 适配器启用：`Get-NetAdapter` 显示 AIC8800 适配器为 "Up"，`NetLinkReported` 1，MAC 是模块的；
   - DHCP 拿到 IP：`ipconfig /all` 显示家里路由器分配的地址、网关和 DNS（`-Status` 也会打印）；
   - ping 网关：`ping -n 1000 <网关>` 丢包低于 1%，`ping -l 1400 <网关>` 也能通（满长帧）；
   - 打开网页：Edge 或 `curl https://example.com` 能加载，100 MB 下载能完成（记下速度；第一个目标是 3 MB/s 或以上）；
   - `NetTxErrors` 0，`NetRxDrops` 很小；路由器重启后链路能自己恢复；重启电脑后无需操作即可重连。
   冷启动 n = 5 次，必须全部通过。这就是 Wi-Fi 的发布标准。如果阶段 3 能加入但一个帧都回不来（`NetRxFrames` 0，路由器根本没看到 DHCP 请求），怀疑 TX：把 `NetTxFrames` 和路由器的计数对比，并尝试 TX 功率表（见下）。

## 蓝牙

固件下载完以后，PID_8D81 的接口 0 和 1 的类是 E0/01/01，即标准的 USB 蓝牙 HCI。根据下面的证据，本仓库不需要蓝牙代码，也不需要 INF；之后列出的未决问题要在板上确定。

**D80 不需要厂商 HCI 初始化。** ROM 补丁和蓝牙模式（`btmode` 5，"仅蓝牙，无外部开关"；`btport` 1，USB）是加载器阶段作为补丁表的一部分写进去的（`aic_fw.c`，`aicbt_patch_table_load`），和 AICSemi 的 `aic_load_fw` 一样。AICSemi 自己的 `aic_btusb.c`（radxa-pkg/aic8800，`src/USB/driver_fw/drivers/aic_btusb`）在 `btusb_probe` 里只有 `g_chipid == PRODUCT_ID_AIC8800DC || g_chipid == PRODUCT_ID_AIC8800D80N` 时才调用 `download_patch()`；PID 0x8D81 对应 `PRODUCT_ID_AIC8800D80`，所以对这个模块 probe 什么都不发，直接注册一个普通的 HCI 设备。`DOWN_FW_CFG` 和 `GET_USB_INFO` 两个 ioctl 里的 `download_patch` 被注释掉了。文件里其余的厂商命令（`HCI_VSC_SET_ADFILTER_*`、APCF）属于 Android 的 Bluedroid 路径；Armbian 用 BlueZ 编译它（`fix-aic_btusb-use-bluez-by-default.patch`），不会发这些命令。Linux 的通用 `btusb` 也会按类绑定同一个接口。

**BthUsb 按类绑定。** 泰山派安装用的 Windows 11 23H2 ARM64 `install.wim` 里的 `C:\Windows\INF\bth.inf`（DriverVer 10.0.22621.2215）在 NTarm64 下有：

```
Generic Bluetooth Adapter= BthUsbGeneric, USB\Class_E0&SubClass_01&Prot_01
Generic Bluetooth Adapter= BthUsbGeneric, USB\MS_COMP_BLUTUTH
```

所以只要 aic8800usb 的加载器跑过、芯片以 8D81 重新出现，系统自带的 `bthusb.sys` 就会按兼容 ID 装到接口 0 上，不需要我们的 INF。

**未决，要在板上测：**

1. *接口分组。* Windows 的复合设备驱动只有在设备声明了接口关联描述符（IAD）时，才会把接口 0（HCI 事件和 ACL）和接口 1（SCO，等时传输）合成一个功能。有 IAD 时 BthUsb 拿到两个接口，只出现一个 "MI_00" 设备。没有 IAD 时 MI_00 和 MI_01 是两个兼容 ID 相同的独立设备：BthUsb 跑在 MI_00 上（ACL 可用，所以配对、A2DP、HID 都能用；耳机免提协议要的 SCO 不行），第二个 BthUsb 实例会去装 MI_01，它没有事件和 ACL 端点，预计带问题代码失败。真出现这种情况，修法是给 `USB\VID_A69C&PID_8D81&MI_01` 一个空 INF（硬件 ID 匹配优先于类匹配），参照 `null-devices` 的做法。先在 Armbian 上查：`lsusb -v -d a69c:8d81 | grep -A6 "Interface Association"`。
2. *蓝牙地址。* Windows 要求 `HCI_Read_BD_ADDR` 返回非零地址；固件报不出地址的话，无线电起不来（Linux 的 `btusb` 会显示 `00:00:00:00:00:00`）。
3. *`AICBT_MODE_T`。* 如果无线电起来了但扫描不到东西，下一个怀疑对象是写进补丁表的蓝牙模式值。

**回归检查。** 本分支上的 `tools/regress/boards/rock4d.json` 把 `network.bluetooth` 设为 true，`network.bluetoothDevice` 设为 `USB\VID_A69C&PID_8D81&MI_00`；`regress.ps1` 于是要求这个设备正常，且至少有一个蓝牙类设备正常（`net.bluetooth`）。

**板上测试（阶段 1 通过之后）。**

1. 设备管理器：蓝牙下有 "Generic Bluetooth Adapter"，实例为 `USB\VID_A69C&PID_8D81&MI_00`，服务 BTHUSB，无问题代码；记下 MI_01 是否存在及其状态（上面第 1 点）。`Get-PnpDevice -PresentOnly | ? InstanceId -like 'USB\VID_A69C*' | ft Status,Class,FriendlyName,InstanceId`。
2. `regress.ps1`：`net.bluetooth` 为 PASS。
3. 设置 > 蓝牙和其他设备：有蓝牙开关；扫描能找到手机并配对（两边确认配对码）。
4. 蓝牙耳机：配对，选为输出，播放本地音频文件 10 分钟，记录断音。立体声 A2DP 是通过标准；耳机通话（HFP）只有在有 IAD 时才预期可用。
5. 冷启动后重复 3 和 4（已配对设备能重连），以及在 Wi-Fi 阶段 4 同时连着的情况下重复（共存：两者用同一个 2.4 GHz 射频；记录下载时音频是否断）。
6. 失败时要保留的数据：`pnputil /enum-devices /connected /class Bluetooth`、系统日志里的 BTHUSB 事件、aic8800usb 的 `LastStep`。

## 风险与未决问题

- **端点顺序。** 数据和消息管道按 AICSemi 的方式选（第一个 bulk IN/OUT 走数据，第二个走消息）。如果固件在另一个管道上应答也不要紧：两个 IN 管道都在读，每个包按类型解析。如果它要求消息走数据 OUT 管道，`LastError` 会写出第一条没有确认的消息。
- **零长度包。** Linux 发消息时带 `URB_ZERO_PACKET`；驱动在消息正好填满整包时会再发一个空传输（目前的消息都不会这样）。
- **没有 RX 重排，没有固件 credit。** TX 流控只靠 32 个在途 USB 写；RX 帧可能乱序。够 DHCP 和浏览网页用，吞吐量会有损失。
- **TX 功率表。** 固件可能用内置的功率表发送（扫描的 probe request 和关联是它发出的第一批帧）；如果不行，首先要补的就是这些表。
- **只开 HT20、关掉省电、没有 TX 功率表。** 为第一次上板测试而选；使用固件的默认值。
- **握手消息 4 的竞争。** 和 wpa_supplicant 一样，先发消息 4，紧接着（20 ms 后）装成对密钥。如果某个 AP 因为消息 4 被加密了而丢弃它，就要改成等 TX 确认（带确认索引的 `status_desc_addr`）再装密钥。
- **USB 速度。** AICSemi 在芯片不在高速或 SuperSpeed 端口上时会重启它；本驱动只记录 `UsbHighSpeed`，不做检查。

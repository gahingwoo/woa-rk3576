# Wi-Fi and Bluetooth on the Radxa ROCK 4D (AIC8800D80 over USB)

English | [简体中文](aic8800.zh-CN.md)

Status, 2026-11-25: the driver `drivers/net/aic8800usb` (branch
`aic8800-usb`) downloads the firmware, scans and joins a WPA2-PSK network
with its own supplicant. **Nothing here has run on a board.** The protocol
code passes host tests against a simulated chip and access point
(`tools/aictest`), the download runs in CI with the real firmware files, and
every message ID and parameter offset is checked at compile time against
AICSemi's own headers. It has no network adapter yet, so Windows shows no
Wi-Fi.

## The hardware

The production ROCK 4D carries an AICSemi AIC8800D80 Wi-Fi 6 and
Bluetooth 5.4 combo on USB (module listed as FCU760K by CNX Software). The
Radxa Dragon Q6A has the same chip. edk2-rk3576's ROCK 4D platform code
already powers it at boot (GPIO2 PC7 `vcc_3v3_wifi`, GPIO2 PD1 rfkill), so
it enumerates on the DWC3 host without anything from Windows.

The chip has two USB faces:

| USB ID | When | Interfaces |
|---|---|---|
| `VID_A69C&PID_8D80` | at power-on: the ROM loader | one vendor interface (FF/FF/FF), bulk IN and OUT |
| `VID_A69C&PID_8D81` | after the firmware download | MI_00 and MI_01: Bluetooth HCI (E0/01/01); MI_02: WLAN (FF/FF/FF), two bulk IN and two bulk OUT |

## The existing Windows driver and 23H2

Mario Bălănică's `aicwlan` (worproject/dldserv-mirror, release asset
`aicwlan_arm64_0935761.zip`) is a WiFiCx driver for this chip. It is a
binary without a licence, so it can be used but not copied, changed or
shipped here. Its INF installs only on Windows 11 24H2 and later
(`NTARM64.10.0...26100`), and 24H2 cannot boot on the RK3576 (ARMv8.0, no
LSE atomics). Whether the binary itself needs 24H2 was checked by reading its
WDF bind information (`aicwlan.sys` from that zip, with the symbols in its
`aicwlan.pdb`):

| | aicwlan.sys binds | Windows 11 22621 (22H2/23H2) has |
|---|---|---|
| KMDF | 1.33, `WdfMinimumVersionRequired` 33 | 1.33 |
| NetAdapterCx | 2.2 (124 functions) | 2.3 ([version table](https://learn.microsoft.com/en-us/windows-hardware/drivers/netcx/netadaptercx-version-overview)); 2.2 is what WiFiCx drivers must bind on 22H2 |
| WiFiCx | **1.2** (40 functions), `WifiMinimumVersionRequired` **2** | **1.0** |
| ntoskrnl, HAL, WppRecorder | 23 ordinary imports (`ExAllocatePool2`, `Zw*File`, `KeWaitForSingleObject`, ...) | all present (`ExAllocatePool2` since 2004) |

The WiFiCx row decides it. `wificx.sys` from a 22621.2428 image
(10.0.22621.2215) registers its class library as version 1.0
(`WdfClassLibraryInfo` from Microsoft's public symbols). Microsoft's
[WiFiCx versioning page](https://learn.microsoft.com/en-us/windows-hardware/drivers/netcx/building-a-wificx-driver-for-multiple-versions-of-windows)
says 21H2 and 22H2 support WiFiCx 1.0 only, 1.1 and 1.2 start with Insider
build 25330 (the 24H2 line), and a 1.1/1.2 driver runs on 1.0 only if it is
built with `WIFI_MINIMUM_VERSION_REQUIRED=0`. aicwlan is built with 2.
So lowering the INF floor will let it install on 23H2, but the class
extension bind should fail at driver start (expected: Code 10 or 31, a
WiFiCx version mismatch in the event log). The only ways to run it on 23H2
are a rebuild by its author with the minimum version set to 0 (and runtime
checks around any 1.1/1.2 calls), or a driver of our own. This repository
does not patch the binary.

## Private trial of aicwlan on 23H2

Cheap, confirms the analysis, and is for the board owner only: the edited
INF stays on the board and is never committed, published or put in an image.

1. ROCK 4D, Windows 11 23H2 (22631), test signing on (`bcdedit /set
   testsigning on`, as on the other boards). Confirm the loader enumerates:
   `pnputil /enum-devices /connected | findstr A69C` shows
   `USB\VID_A69C&PID_8D80`.
2. Unpack `aicwlan_arm64_0935761.zip` into a folder on the board. In
   `aicwlan.inf` change both `NTARM64.10.0...26100` to
   `NTARM64.10.0...22621` (the `[Manufacturer]` line and the models section
   name). Nothing else.
3. Make a catalog and sign it with a local certificate (on any PC with the
   WDK): `inf2cat /driver:<folder> /os:10_NI_ARM64`, then
   `signtool sign /fd sha256 /f test.pfx /p <pw> <folder>\aicwlan.cat`. The
   `.sys` keeps Mario's own test signature. Import `test.cer` into Root and
   TrustedPublisher on the board (`certutil -addstore -f`).
4. Stage only, never hot-install: `pnputil /add-driver <folder>\aicwlan.inf`,
   then restart Windows.
5. Read: Device Manager state of the loader device and its problem code;
   `Get-WinEvent -LogName System -MaxEvents 50 | ? ProviderName -match
   'wdf|kernel-pnp|aicwlan'`; `C:\Windows\INF\setupapi.dev.log` for the bind.
   Expected: the loader device gets aicwlan, starts the firmware or not, and
   the driver fails to start with a WiFiCx version error. Pass (unexpected):
   a Wi-Fi adapter appears and `netsh wlan show networks` lists networks.
6. Remove it afterwards: `pnputil /enum-drivers` to find its `oemNN.inf`,
   `pnputil /delete-driver oemNN.inf /uninstall`, restart.

## Firmware files

The driver loads, from `C:\Windows\System32\drivers\aic8800`:

| File | Size | Role |
|---|---|---|
| `fw_patch_table_8800d80_u02.bin` | 1384 | the patch table: where the next files go, the ROM trap and patch pairs, Bluetooth mode |
| `fw_adid_8800d80_u02.bin` | 1708 | ROM patch data |
| `fw_patch_8800d80_u02.bin` | 32700 | ROM patch code |
| `fw_patch_8800d80_u02_ext0.bin` | 16136 | extra patch named by the table |
| `fmacfw_8800d80_u02.bin` | 358072 | the Wi-Fi firmware (or `fmacfw_8800d80_h_u02.bin`, 358640, on an "H" chip) |

They are AICSemi's. Radxa's package ships them, and its `debian/copyright`
puts all of `src/` under GPL-2, but these are binaries without source and
AICSemi publishes no licence for them, so this repository does not
redistribute them. `install-firmware.ps1` downloads them on the board from
radxa-pkg/aic8800 at the pinned commit and checks each SHA-256 and size,
like the Broadcom installer does. They are byte-identical to the copies in
the aicwlan zip.

## The USB protocol

All from AICSemi's driver (file references in `aic_proto.h`):

- **Packets.** Every bulk transfer holds packets starting with `u16 len`
  (12 bits), `u8 type`, `u8 0`. Host to device: a control message is type
  0x11, a dummy word, then the LMAC header (`id`, `dest task`, `src task` =
  100, `param_len`) and the parameters; a data frame is type 0x01 with the
  28-byte host descriptor and the Ethernet payload, padded to 4 bytes, with
  one extra byte when the transfer would end on a 512-byte boundary. Device
  to host: types with bit 0x10 are messages (0x11 a confirm or indication,
  E2A header with a pattern word; 0x12 a TX confirm; 0x13 firmware console
  text); the rest are data packets: a 60-byte RX header (length, decryption
  status, VIF/station indices) and the 802.11 frame.
- **Message IDs** are `task << 10 | index` (MM 0, DBG 1, SCANU 4, ME 5,
  SM 6). Each request names the confirm the driver waits for.
- **Firmware download** (ROM loader, DBG task): read the chip ID at
  0x40500000; write the adid, patch and ext files where the table's
  `AICBT_PINF_T` section says (0x201940, 0x1E0000, 0x20B43C for the
  current files) in 1024-byte `DBG_MEM_BLOCK_WRITE`s; write every
  (address, value) pair of the table (140 for the current one), with the
  Bluetooth settings put into its `AICBT_MODE_T` section; write `fmacfw` at
  0x120000; the "patch config" (find the config base and patch block through
  pointers at 0x120198/0x1201A0/0x1201A4 in the image, write the `PTCH`
  magic and three settings); `DBG_START_APP` at 0x120000. The chip leaves
  the bus and comes back as PID_8D81.
- **Runtime init**: `MM_SET_STACK_START`, `MM_GET_FW_VERSION`,
  `MM_SET_RF_CALIB`, `MM_GET_MAC_ADDR`, `MM_RESET`, `MM_VERSION`,
  `ME_CONFIG` (HT20 only for now), `ME_CHAN_CONFIG`, `MM_START`,
  `MM_ADD_IF` (station).
- **Scan**: `SCANU_START` (all 2.4 GHz channels and 25 5 GHz ones, one
  wildcard SSID); each beacon or probe response arrives as
  `SCANU_RESULT_IND`, the end as `SCANU_START_CFM`.
- **Join**: `SM_CONNECT` with the RSN IE, `CONTROL_PORT_HOST` and
  `WPA_WPA2_IN_USE`; `SM_CONNECT_IND` gives the AP's station index. The
  firmware does not run WPA2 itself: the 4-way handshake arrives as EAPOL
  data frames and the host answers like wpa_supplicant does on Linux, then
  installs the keys with `MM_KEY_ADD` and opens the port with
  `ME_SET_CONTROL_PORT`.
- **Data**: TX gives the firmware Ethernet payloads plus addresses and
  ethertype; RX gives the host decrypted 802.11 frames, which the host turns
  into Ethernet (strip the 802.11, security and LLC/SNAP headers; split
  A-MSDUs).

## Driver design and stages

Same shape as `bcmwlsdio` (the TaishanPi 3M Broadcom driver): a portable
core with no Windows or libc dependency (`aic_*.c`, built with
`-ffreestanding -nostdinc` in CI), thin KMDF files around it (`driver.c`,
`usb.c`, `files.c`), a `Stage` setting so each board session tests one
step, and a host test with a simulated chip (`tools/aictest`).

```
  (next) NetAdapterCx adapter, then WiFiCx 1.0
  -------------------------------------------------
  aic8800usb.sys (KMDF, Class System for now)
    driver.c    PnP, worker thread running the stages, registry records
    usb.c       pipes, continuous readers into a ring, bulk OUT
    files.c     firmware files
    -- portable core --
    aic_core.c  framing, command/confirm, receive dispatch
    aic_fw.c    chip ID, patch table, download, start
    aic_wlan.c  runtime init, scan, join, keys, indications
    aic_data.c  Ethernet <-> firmware data frames, A-MSDU
    aic_wpa.c   WPA2-PSK supplicant (4-way and group handshakes)
    aic_crypto.c SHA-1, HMAC, PBKDF2, PRF, AES-128, key wrap
  -------------------------------------------------
  usbccgp (PID_8D81) / usbhub3 / DWC3 xHCI (in-box)
```

Why not WiFiCx straight away: the same WDI command and task set as for the
Broadcom chip (see that design), plus WiFiCx 1.0 is the only version 23H2
has. Everything below the Windows Wi-Fi interface (download, init, scan,
join, keys, data conversion) is the same in all three models, so it is
built and tested first.

One driver binds both USB faces. The loader instance downloads and records
`FirmwareLoaded` in a volatile key (`Parameters\Boot`); the runtime
instance, if it finds no such record (firmware left running across a warm
reboot), sends `DBG_START_APP` with the reboot type so the chip returns to
its loader, as AICSemi's Linux driver does, at most twice per boot.

| Stage | Loader (PID_8D80) | Runtime (PID_8D81 MI_02) |
|---|---|---|
| 0 | select the configuration, list pipes, record USB identity and speed; nothing sent | same |
| 1 | + chip ID, firmware download and start | + chip ID through the firmware |
| 2 | (as 1) | + init, MAC, firmware version, station VIF, scan to `ScanResults` |
| 3 | (as 1) | + join `Ssid` with WPA2-PSK, keys, port; keep the link (rekeys, reconnect) |

## Registry values

Settings live in the service key
`HKLM\SYSTEM\CurrentControlSet\Services\aic8800usb\Parameters` (one place
for both instances): `Stage`, `Ssid`, `Passphrase` (replaced by `Pmk`,
REG_BINARY, on first use), `FirmwareDir`, `ScanTimeoutMs`,
`ConnectTimeoutMs`. `aic-bringup.ps1` writes them.

Records go to each instance's Device Parameters (`aic-bringup.ps1 -Status`
prints them):

| Value | Meaning |
|---|---|
| `LastStep`, `PrevStep`, `StepSeq` | where the worker is or stopped; flushed each step |
| `OpenStatus`, `UsbVid`, `UsbPid`, `UsbInterface`, `UsbHighSpeed`, `UsbBulkIn`, `UsbBulkOut`, `UsbOutMaxPacket` | stage 0 |
| `ChipWord`, `ChipRev` (3 = U02, 7 = U03), `ChipSubRev`, `ChipIsH`, `ChipMcu` | chip ID |
| `FwFileStatus` | NTSTATUS if a firmware file could not be read |
| `PatchSections`, `PatchWrites`, `PatchVersion`, `FwVersionWord`, `FwState` | the download (`started` on success) |
| `FwVersion`, `MacAddress`, `Is5gSupported`, `LmacVersion`, `FwFeatures` | runtime init |
| `ScanResults` (SSID, BSSID, MHz, dBm, security per line), `ScanCount`, `ScanStatus` | scan |
| `ConnectStatus` (802.11 status), `HandshakeMsg` (last EAPOL message handled, 4 = done), `LinkFreq`, `LinkBssid`, `LinkState` (3 = up), `Reconnects`, `DisconnectReason` | join |
| `TxMsg`, `RxMsg`, `RxInd`, `RxData`, `RxDataDropped`, `RxEapol`, `TxData`, `RxPrint`, `RxErrors`, `RxUnknown`, `LastUnknownMsg`, `FwPanic`, `MicFailures` | core counters |
| `UsbSends`, `UsbSendErrors`, `UsbLastSendStatus`, `UsbRingDrops`, `UsbReaderErrors` | USB counters |
| `LastError` | the core's last error text |

## Board test plan

ROCK 4D, Windows 11 23H2, test signing on, Ethernet for access. Install as
in [the driver's README](../../drivers/net/aic8800usb/README.md): import
`signer.cer`, run `install-firmware.ps1`, `pnputil /add-driver` (stage
only), set the stage with `aic-bringup.ps1`, restart. After each restart,
`aic-bringup.ps1 -Status`, and keep a serial log of the firmware boot. Do
not run the aicwlan trial and this driver at the same time (both bind
`PID_8D80`); remove one before installing the other.

1. **Stage 0.** Pass: the loader device is "AIC8800D80 USB Wi-Fi
   (firmware loader, bring-up)", OK state, `OpenStatus` 0, `UsbPid` 0x8D80,
   `UsbBulkIn` 1 or more, `UsbBulkOut` 1 or more, `UsbHighSpeed` 1.
2. **Stage 1.** Pass: on the loader `ChipRev` 3 or 7, `FwState`
   `started`, `PatchWrites` 140, `PatchVersion` names the table's build,
   `FwVersionWord` 0x06090101; then a new device `PID_8D81&MI_02` appears
   with the runtime description, `UsbBulkIn` 2, `UsbBulkOut` 2, and its
   `LastStep` "runtime: identify" with the same `ChipRev`. Bluetooth MI_00
   shows up as a Bluetooth radio (see [Bluetooth](#bluetooth)).
   Fail cases to note: `FwFileStatus` (files missing), `LastError`
   "no confirm for message 0x0400" (the loader does not answer: endpoint
   choice or framing), the chip never returning as 8D81.
3. **Stage 2.** Pass: `FwVersion` a real string, `MacAddress` the module's
   address (compare with Armbian's `ip link`), `ScanCount` > 0 and the home
   network in `ScanResults` with a plausible RSSI; repeat over 3 boots.
   Compare with `iw dev wlan0 scan` on Armbian in the same place.
4. **Stage 3.** `aic-bringup.ps1 -Stage 3 -Ssid <home> -Passphrase <...>`.
   Pass: `LinkState` 3, `HandshakeMsg` 4, `ConnectStatus` 0, `MicFailures`
   0, `RxData` growing between two `-Status` readouts a minute apart (the
   LAN's broadcasts arrive decrypted), the router's client list shows the
   module's MAC; still up after 30 minutes (one group rekey on most
   routers), and back after the router is restarted (`Reconnects`). n = 5
   cold boots, all must pass. A wrong passphrase must give
   `HandshakeMsg` 2 and a "4-way handshake did not complete" `LastError`.

The release bar (joins the home WPA2 network and gets online) needs the next
stage: the network adapter.

## Bluetooth

After the firmware download, interfaces 0 and 1 of PID_8D81 are class
E0/01/01, a standard Bluetooth HCI over USB. The ROM patches and the
Bluetooth mode (`btmode` 5, "BT only, no external switch"; `btport` 1, USB)
are written by the loader stage as part of the patch table, the same as
AICSemi's `aic_load_fw` does; AICSemi's own `aic_btusb` sends no further
vendor commands for the D80 (its patch download runs only for the 8800DC
and D80N). So the in-box BthUsb should bind by class and work with no driver
from this repository, once aic8800usb's stage 1 has run. To check in the
stage 1 session: Device Manager shows a Bluetooth radio under the 8D81
device, Settings can scan for and pair a phone. If it does not come up, the
next suspects are the BD address (the firmware may report none, and Windows
then refuses the radio) and the `AICBT_MODE_T` values.

## Next stages

1. **Network adapter (the release bar).** Make the runtime instance a
   NetAdapterCx client, as `dwc_eqos` is: media 802.3, MAC from
   `MM_GET_MAC_ADDR`, TX through `aic_build_tx` on the data pipe, RX from
   `aic_rx_to_eth` into the RX ring, link state from the core. The INF moves
   to Class Net for PID_8D81 MI_02 (a second INF; the loader stays Class
   System). Accept: DHCP lease, `ping` the gateway 1000 times with under 1 %
   loss, a 100 MB download, reconnect after an AP restart, n = 5 boots.
   Then: RX reordering for A-MPDU (`flags_need_reord`), the TX credit
   indications, the TX power tables from `aic_userconfig_8800d80.txt`.
2. **WiFiCx 1.0** (22621 has no later version) so Windows shows Wi-Fi and
   runs its own supplicant (EAPOL over the data path, keys through
   `MM_KEY_ADD`), with the scan and connect tasks mapped to
   `SCANU_START` and `SM_CONNECT`.

## Risks and open questions

- **Endpoint order.** Data and message pipes are picked as AICSemi does (the
  first bulk IN/OUT carry data, the second the messages). If the firmware
  answers on a different pipe, nothing breaks: both IN pipes are read and
  every packet is parsed by its type. If it expects messages on the data
  OUT pipe, `LastError` names the first message without a confirm.
- **Zero-length packets.** Linux sends messages with `URB_ZERO_PACKET`; the
  driver sends an empty transfer after a message that fills whole packets
  (none of the current messages do).
- **No TX flow control, no RX reordering.** Fine for the handshake; needed
  for throughput in the adapter stage.
- **HT20 only, power save off, no TX power tables.** Chosen for the first
  board tests; the firmware's defaults apply.
- **The handshake's message 4 race.** As wpa_supplicant does, message 4 is
  sent and the pairwise key installed right after (20 ms later). If an AP
  drops message 4 because it arrived encrypted, the delay needs to wait for
  the TX confirm instead (`status_desc_addr` with a confirm index).
- **USB speed.** AICSemi reboots the chip if it is not on a high-speed or
  SuperSpeed port; the driver records `UsbHighSpeed` and does not check.

# EC20 4G on the TaishanPi 3M: mobile data under Windows

The LCKFB TaishanPi 3M carries a Quectel EC20 (USB `2C7C:0125`, firmware
EC20CEFILGR08A03M1G on the test board). The goal is mobile data in Windows
11 23H2 through Windows' own mobile broadband stack (the in-box MBIM class
driver and Settings > Network & internet > Cellular), with no Quectel
driver. The module's drivers and helper scripts for Windows (COM ports, AT
tool, PIN, GNSS, call audio) live in their own repository,
[gahingwoo/ec20-woa](https://github.com/gahingwoo/ec20-woa); this page
records the architecture decision and the board plan, and
[`tools/ec20`](../../tools/ec20) has the mode switch for both OSes.

Status: nothing on this page has run in MBIM mode on the board yet. What
was measured is marked as such.

## The decision

The EC20 ships in QMI/rmnet mode (`AT+QCFG="usbnet",0`), for which Windows
has no driver. `AT+QCFG="usbnet",2` turns its network function into CDC
MBIM, which Windows drives with an in-box driver. The setting is kept in the
module's NV memory and survives power cycles, so whatever the last OS set is
what the next OS sees.

The question was whether the mode has to follow the OS (a Windows driver
resetting it before shutdown, or the UEFI firmware setting it at handoff).
It does not: Linux on the same board (Armbian, mainline drivers,
ModemManager) supports the EC20 in MBIM mode as well as in QMI mode,
including the board's voice calls, on the evidence below. So the plan is a
**one-time switch to MBIM**, done from either OS, and nothing in the
firmware. The per-OS options are written down at the end, with their cost,
in case the board test finds something Linux loses in MBIM mode.

## Why one mode is enough: Linux in MBIM mode

**Kernel.** From the mainline tables (read in a linux-next tree from
2026-09):

- `drivers/usb/serial/option.c` binds the EC25/EC20 PID by interface class
  only: `USB_DEVICE_AND_INTERFACE_INFO(QUECTEL_VENDOR_ID,
  QUECTEL_PRODUCT_EC25, 0xff, 0xff, 0xff)` with `NUMEP2` (the DIAG port,
  two endpoints) and `(..., 0xff, 0, 0)` (NMEA, AT, modem). Those
  interfaces are the same in both modes, so ttyUSB0 to ttyUSB3 stay.
- `drivers/net/usb/qmi_wwan.c` has `QMI_MATCH_FF_FF_FF(0x2c7c, 0x0125)`:
  it binds the FF/FF/FF network interface, which MBIM mode no longer has.
- `drivers/net/usb/cdc_mbim.c` matches any `USB_CLASS_COMM` /
  `USB_CDC_SUBCLASS_MBIM` interface, no VID/PID needed, so it binds the EC20
  in MBIM mode. The kernel needs `CONFIG_USB_NET_CDC_MBIM`; Armbian's
  rockchip64 (current, edge) and rk35xx vendor kernel configs set it to `m`.

**ModemManager.** The Quectel plugin (`src/plugins/quectel/mm-plugin-quectel.c`,
ModemManager main as of 2026-11-17) sets `MM_PLUGIN_ALLOWED_MBIM` and, when
the probes find an MBIM port, creates a `MMBroadbandModemMbimQuectel`.
`MMBroadbandModemMbim` derives from `MMBroadbandModem`, which implements
the Voice interface over AT (`G_IMPLEMENT_INTERFACE
(MM_TYPE_IFACE_MODEM_VOICE, ...)` in `mm-broadband-modem.c`), and neither
MBIM class overrides it. So calls keep working through ModemManager (and
GNOME Calls) in MBIM mode, by AT commands on ttyUSB2 instead of QMI's
voice service. Data is an MBIM bearer through NetworkManager as usual.

**Voice audio on this board.** The call-audio fix (the BSP's
`lckfb-tspi-3m-modem-voice`, see the EC20 notes in the Armbian BSP) is
AT only: interface 02 enables UAC in `AT+QCFG="USBCFG"` and waits for the
SIM, interface 03 (`ID_MM_PORT_IGNORE=1`) sends `AT+QPCMV=1,2` after
registration. The udev rules key on `ID_USB_INTERFACE_NUM` 02 and 03, which
do not move in MBIM mode. The UAC function moves up (it follows the two MBIM
interfaces) and is still bound by class by `snd-usb-audio`.

**Risks, to check on the board:**

- `early()` in the BSP script rewrites `USBCFG` only when it has exactly 9
  fields and UAC is off. In MBIM mode the `rmnet` field may read differently;
  UAC is already on (stored), so it should not write, but read the value
  once in MBIM mode.
- A ModemManager maintainer wrote in 2020 that an EC25 in MBIM mode did not
  support MM's initial EPS bearer settings. The test SIM is VoLTE only; if
  its attach APN ever has to be set from Linux, that is the place it could
  fail.
- Windows' mobile broadband service may write APN profiles into the module
  (provisioned contexts persist). Linux then sees a different default APN.

## What Windows needs

**An AT port, to switch.** The AT interface (MI_02) is vendor class
FF/00/00. Windows binds nothing to it by itself (usbser.sys loads by class
only for CDC ACM, 02/02), so on a clean install the module has no COM port.
`ec20-ports.inf` from ec20-woa binds the in-box `usbser.sys` to MI_00..MI_03
by hardware ID; measured on the board 2026-11-14: four COM ports, `AT`
answers on the AT port (COM6). No new INF is needed here. Without it, do the
switch from Linux.

**The MBIM driver.** `netwmbclass.inf` in the 23H2 ARM64 image
(DriverVer 10.0.22621.1, read from the TaishanPi's `install.wim`) matches
`USB\class_02&subclass_0e&prot_00` and `USB\MS_COMP_MBIM`, service
`cxwmbclass` (`cxwmbclass.sys`, the MBBCx-based driver). No INF from us.
It needs the two MBIM interfaces (02/0E/00 control, 0A/00/02 data) grouped
into one function, which Windows' composite driver does only with an
Interface Association Descriptor. Qualcomm's MBIM gadget function, on which
this firmware is built, declares one, but this module is unmeasured; the
mode scripts report a separate data interface as a failure.

**No INF on MI_04.** The regression suite whitelists
`USB\VID_2C7C&PID_0125&MI_04` (no driver in QMI mode). No INF must bind that
hardware ID, not even a null one: it would outrank the MBIM driver's class
match after the switch, since the hardware ID is the same in both modes.

**Firmware revision.** An EC25-AU on Quectel's forum accepted `usbnet,2`
only after a firmware update, and Quectel staff say some variants do not
support MBIM. The scripts read the mode back before and after the reset and
stop if it did not stick.

**SIM and APN.** Windows asks for the SIM PIN itself. It picks the APN from
its own operator database by the SIM's IMSI/ICCID; if the operator is not in
it, add the APN in Settings > Network & internet > Cellular > Advanced
cellular settings > Add an APN (type "Internet and attach" for a VoLTE-only
SIM). Data may be metered; "Let Windows keep me connected" is on by default.

## If it turns out one mode is not enough

Only if the board test finds something Linux cannot do in MBIM mode (and the
fix is not on the Linux side):

- **Switch per OS from the OSes themselves.** A Linux unit sets
  `usbnet,0` at boot if it reads 2, a Windows scheduled task sets 2 if it
  reads 0. Cost: one extra module reset (20 to 40 s without the modem)
  on the first boot after changing OS, none otherwise. Simple, no firmware.
- **Switch from UEFI.** The firmware would need its own driver for a
  vendor-class USB interface (bulk endpoints of MI_02, CDC-style control
  line state), wait for the module to answer AT (it takes about 10 s after
  power-up), set the mode for the chosen boot entry before
  `ExitBootServices`, reset it and wait for re-enumeration only when the
  mode changes: 10 to 15 s added to every boot that touches the module,
  20 to 40 s more when it switches, and a USB host stack path in EDK2
  that exists for this one module. Not worth building while the cheaper
  option above exists; not implemented.

A Windows driver resetting the mode at shutdown was rejected: the mode would
be wrong after every crash or power cut, which is exactly when it matters.

## The tools

[`tools/ec20/ec20-mode.ps1`](../../tools/ec20/ec20-mode.ps1) (Windows,
Windows PowerShell 5.1) finds the COM port of MI_02 (or MI_03) by itself:

```powershell
.\ec20-mode.ps1 -Status     # firmware, usbnet, the USB functions and their drivers
.\ec20-mode.ps1             # to MBIM: asks, sets, reads back, resets, waits, checks cxwmbclass
.\ec20-mode.ps1 -Revert     # back to QMI (usbnet 0)
```

[`tools/ec20/ec20-mode.sh`](../../tools/ec20/ec20-mode.sh) (Linux, root)
uses interface 03 by default, which ModemManager ignores on the TaishanPi:

```sh
sudo ./ec20-mode.sh status
sudo ./ec20-mode.sh mbim    # checks cdc_mbim is bound afterwards
sudo ./ec20-mode.sh qmi     # back, checks qmi_wwan
```

Exit codes for both: 0 done and checked; 1 refused or cancelled; 2 the
read-back did not match; 3 no AT port; 4 the module did not come back;
5 the mode is set but the expected driver is not bound. The ec20-woa
`Set-Ec20UsbNet.ps1` does the same with the ec20-woa module and an
explicit `-Port`.

## Board test plan

Both OSes, in this order, on one SIM. Keep each step's output.

**1. Linux, QMI (baseline).** `sudo tools/ec20/ec20-mode.sh status`:
`usbnet: 0`, interface 4 on `qmi_wwan`. Place one call to a known number and
confirm audio both ways (uplink was never confirmed by a person).

**2. Linux, switch.** `sudo tools/ec20/ec20-mode.sh mbim`. Pass: exit 0,
interface 4 on `cdc_mbim`, ttyUSB0..3 unchanged. Record
`lsusb -v -d 2c7c:0125 | grep -B2 -A8 "Interface Association"` (the IAD
question for Windows) and `AT+QCFG="USBCFG"` on ttyUSB3.

**3. Linux in MBIM mode.** `mmcli -m any`: the modem is found by the
Quectel plugin with an MBIM primary port and a `voice` interface; data
connects through NetworkManager (`nmcli c up` on the cellular connection,
`ping -I wwan0 1.1.1.1`); after registration the voice service logs
"voice over USB audio: ok"; place and receive one call each, audio both
ways. Reboot (cold) and repeat the call: 3 boots. Fail: no voice interface
in MM, or silent calls in MBIM but not in QMI (then see the per-OS options).

**4. Windows.** `.\tools\ec20\ec20-mode.ps1 -Status`: `usbnet: 2`, MI_04 class
02/0E with service `cxwmbclass` and status OK, no separate 0A function.
Settings shows Cellular; `netsh mbn show interfaces` and
`netsh mbn show readyinfo *` show the SIM ready. Connect, then
`ping -S <cellular IP> 1.1.1.1`, browse, a 100 MB download. Toggle airplane
mode off and on; reboot twice: Cellular reconnects without the APN being
re-entered. `regress.ps1`: `devmgr` still PASS (a separate MBIM data
function would show up there as a device with no driver).

**5. Back to Linux after Windows.** Data and a call again: Windows may have
written APN profiles into the module (`AT+CGDCONT?` before and after step 4).

**6. Revert path.** `.\tools\ec20\ec20-mode.ps1 -Revert` on Windows, then
`sudo tools/ec20/ec20-mode.sh status` on Linux: `usbnet: 0`, `qmi_wwan`
bound. Switch to MBIM again for daily use.

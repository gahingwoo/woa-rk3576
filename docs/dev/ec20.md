# EC20 4G on the TaishanPi 3M: mobile data under Windows

English | [简体中文](ec20.zh-CN.md)

The LCKFB TaishanPi 3M carries a Quectel EC20 (USB `2C7C:0125`, firmware
EC20CEFILGR08A03M1G on the test board). The goal is mobile data in Windows
11 23H2 through the in-box MBIM class driver and Settings > Network &
internet > Cellular, with no Quectel driver. COM ports, AT tool, PIN, GNSS
and call audio for Windows are in
[gahingwoo/ec20-woa](https://github.com/gahingwoo/ec20-woa);
[`tools/ec20`](../../tools/ec20) has the mode switch for both OSes.

Status: board-tested on Windows 2026-11-26, **no data over MBIM**. The
switch works (`usbnet` 2, MI_04 binds `cxwmbclass`), but this firmware never
answers MBIM OPEN; see [MBIM on this firmware](#mbim-on-this-firmware). Next
try: [RNDIS](#rndis-usbnet-3), not yet tested end to end. Linux in MBIM
mode is not tested yet.

## The decision: switch to MBIM once

The EC20 ships in QMI/rmnet mode (`AT+QCFG="usbnet",0`), which Windows
cannot drive. `AT+QCFG="usbnet",2` makes the network function CDC MBIM,
which Windows drives in-box. The setting is stored in the module's NV memory
and survives power cycles. Linux handles MBIM mode as well as QMI mode,
including voice calls, so the switch is done once, from either OS, and the
firmware does nothing.

## Why Linux keeps working in MBIM mode

From mainline (linux-next, 2026-09) and ModemManager main (2026-11-17):

| Part | In MBIM mode |
|---|---|
| `option.c` | binds the EC25/EC20 PID by interface class (DIAG, NMEA, AT, modem), the same in both modes: ttyUSB0 to ttyUSB3 stay |
| `qmi_wwan.c` | `QMI_MATCH_FF_FF_FF(0x2c7c, 0x0125)` no longer matches |
| `cdc_mbim.c` | matches any `USB_CLASS_COMM` / `USB_CDC_SUBCLASS_MBIM` interface; needs `CONFIG_USB_NET_CDC_MBIM` (`m` in Armbian rockchip64 and rk35xx) |
| ModemManager | the Quectel plugin allows MBIM and creates `MMBroadbandModemMbimQuectel`, which inherits the AT Voice interface from `MMBroadbandModem`: calls keep working over ttyUSB2; data is an MBIM bearer through NetworkManager |
| Call audio (BSP `lckfb-tspi-3m-modem-voice`) | AT only, keyed on `ID_USB_INTERFACE_NUM` 02 and 03, which do not move; the UAC function moves up after the two MBIM interfaces and `snd-usb-audio` still binds it by class |

**Risks, to check on the board:**

- `early()` in the BSP script rewrites `USBCFG` only when it has exactly 9
  fields and UAC is off. In MBIM mode the `rmnet` field may read differently;
  UAC is already on (stored), so it should not write, but read the value
  once in MBIM mode.
- A ModemManager maintainer wrote in 2020 that an EC25 in MBIM mode did not
  support MM's initial EPS bearer settings. The test SIM is VoLTE only; if
  its attach APN ever has to be set from Linux, that is the place it could
  fail.
- Windows' mobile broadband service may write APN profiles into the module
  (provisioned contexts persist). Linux then sees a different default APN.

## What Windows needs

**An AT port, to switch.** The AT interface is vendor class FF/00/00, and
Windows binds nothing to it (usbser.sys loads by class only for CDC ACM,
02/02). `ec20-ports.inf` 2.0 from ec20-woa binds the in-box `usbser.sys` to
every FF/00/00 interface (NMEA, AT, modem) by the compatible ID
`USB\COMPAT_VID_2c7c&Class_ff&SubClass_00&Prot_00`, in every usbnet mode.
Version 1.0 bound MI_00..MI_03 by hardware ID, which in RNDIS mode takes
MI_00 (the RNDIS function) away from the in-box driver. Without it, do the
switch from Linux.

| MI | usbnet 0, QMI | usbnet 2, MBIM | usbnet 3, RNDIS |
|---|---|---|---|
| 00 | DM FF/FF/FF | DM FF/FF/FF | RNDIS E0/01/03 (+ data) |
| 01 | NMEA FF/00/00 | NMEA | (RNDIS data) |
| 02 | AT FF/00/00 | AT | DM FF/FF/FF |
| 03 | modem FF/00/00 | modem | NMEA FF/00/00 |
| 04 | QMI FF/FF/FF | MBIM 02/0E (+ data) | AT FF/00/00 |
| 05 | audio 01 | (MBIM data) | modem FF/00/00 |
| 06 | | audio 01 | audio 01 |

Measured and inferred cells are marked in the ec20-woa README. DM has no
driver in any mode (it shares FF/FF/FF with the QMI function), so the
regression whitelist has MI_00 and MI_02 next to MI_04.

**The MBIM driver.** `netwmbclass.inf` in the 23H2 ARM64 image
(DriverVer 10.0.22621.1, read from the TaishanPi's `install.wim`) matches
`USB\class_02&subclass_0e&prot_00` and `USB\MS_COMP_MBIM`, service
`cxwmbclass` (`cxwmbclass.sys`, the MBBCx-based driver). No INF from us.
It needs the two MBIM interfaces (02/0E/00 control, 0A/00/02 data) grouped
into one function, which Windows' composite driver does only with an
Interface Association Descriptor. Qualcomm's MBIM gadget function, on which
this firmware is built, declares one, but this module is unmeasured; the
mode scripts report a separate data interface as a failure.

**No INF by interface number.** No INF must bind a
`USB\VID_2C7C&PID_0125&MI_xx` hardware ID, not even a null one: a hardware ID
outranks the MBIM and RNDIS drivers' class matches, and every number holds a
network function in some mode (MI_00 RNDIS, MI_04 QMI or MBIM).

**Firmware revision.** An EC25-AU on Quectel's forum accepted `usbnet,2`
only after a firmware update, and Quectel staff say some variants do not
support MBIM. The scripts read the mode back before and after the reset and
stop if it did not stick.

**SIM and APN.** Windows asks for the SIM PIN itself. It picks the APN from
its own operator database by the SIM's IMSI/ICCID; if the operator is not in
it, add the APN in Settings > Network & internet > Cellular > Advanced
cellular settings > Add an APN (type "Internet and attach" for a VoLTE-only
SIM). Data may be metered; "Let Windows keep me connected" is on by default.

## MBIM on this firmware

Measured on the TaishanPi with EC20CEFILGR08A03M1G, a USB trace
(`Microsoft-Windows-USB-USBHUB3`, `Microsoft-Windows-wmbclass`,
`Microsoft-Windows-Wmbclass-Opn`) around a fresh module reset:

- `cxwmbclass` initialises fine: GET_NTB_PARAMETERS, RESET_FUNCTION,
  SET_NTB_INPUT_SIZE, data interface alt 1, all completed.
- It sends MBIM OPEN (SEND_ENCAPSULATED_COMMAND, 16 bytes; the module
  ACKs the transfer), then again at 12 s and 36 s, then CLOSE at 72 s.
  The interrupt IN transfer that would carry RESPONSE_AVAILABLE never
  completes: the module never answers.
- At about 80 s the driver halts and the device shows code 43
  (CM_PROB_FAILED_POST_START). `pnputil /restart-device` gives another
  80 s of "OK" and the same end. No WWAN interface is ever created, so
  `netsh mbn show interfaces` is empty and the WWAN-SVC log stays empty.

It is not start-up timing (same after a reset, a reboot and a restart
minutes later) and not the SIM (OPEN comes before any SIM access; a
PIN-locked SIM shows as "PIN required" in an open device). A Quectel forum
report on EC20CEFAG firmware says the same: "no response in MBIM mode".
`ec20-mode.ps1` now waits for the interface and exits 6 in this case.

Next steps, in order:

1. Linux in MBIM mode (test plan step 3): `mbimcli -d /dev/cdc-wdm0
   --query-device-caps`. A timeout there too settles it as firmware.
2. Ask Quectel for an EC20CE firmware with working MBIM.
3. Fallback without a Quectel driver: `usbnet` 3, see below.

Each failed start leaves a "Cellular N" network interface (Not Present,
same PnP instance, in `Control\Network\{4D36E972-...}` and
`Control\NetworkSetup2\Interfaces`). They are harmless; they only push the
next name to "Cellular 18".

## RNDIS (usbnet 3)

The in-box `wceisvista.inf` matches `USB\Class_E0&SubClass_01&Prot_03`. It
is an Ethernet adapter ("Remote NDIS based Internet Sharing Device"), not a
Cellular one: no Settings page, no SIM PIN prompt, no APN UI. The module
dials and runs NAT, and the adapter gets a private address by DHCP from it.

Measured on the TaishanPi (2026-11-26): `AT+QCFG="usbnet",3` answers ERROR
and reads back 3 (same quirk as usbnet 2); after `AT+CFUN=1,1` the classes
are as in the table above. With ec20-ports.inf 1.0 MI_00 got usbser and
failed (code 10), and MI_04/MI_05 had no driver.

Dial: Quectel's ECM/RNDIS dial `AT+QNETDEVCTL=<op>,<cid>,<urc_en>`
(`1,1,1` = connect context 1 with URCs) exists on the EC200 line; an EC25-E
forum report says EC2x firmware does not know it, and EC2x guides for ECM
only set the APN and reset (the module dials after registration).
`-Connect` asks `AT+QNETDEVCTL=?` first and dials only if it is supported.

Linux in RNDIS mode (inferred): `rndis_host` binds interface 0, `option`
still creates ttyUSB0..3, now on interfaces 2 to 5. The BSP call-audio
service keys on interface numbers 02 and 03 and breaks in this mode; switch
back with `ec20-mode.sh qmi` (it finds the AT port by class).

## If one mode is not enough

Only if the board test finds something Linux cannot do in MBIM mode:

- Switch per OS from the OSes: a Linux unit sets `usbnet,0` at boot if it
  reads 2, a Windows scheduled task sets 2 if it reads 0. Costs one module
  reset (20 to 40 s) on the first boot after changing OS.
- Switch from UEFI: needs a firmware driver for the vendor-class AT
  interface and adds 10 to 15 s to every boot, 20 to 40 s more on a switch.
  Not implemented.

A Windows driver resetting the mode at shutdown was rejected: the mode would
be wrong after every crash or power cut.

## The tools

[`tools/ec20/ec20-mode.ps1`](../../tools/ec20/ec20-mode.ps1) (Windows,
Windows PowerShell 5.1) probes every usbser COM port of VID 2C7C with `AT`
and uses the first that answers:

```powershell
.\ec20-mode.ps1 -Status                     # firmware, usbnet, the USB functions and their drivers
.\ec20-mode.ps1 -Mode rndis                 # asks, sets, reads back, resets, checks wceisvista + adapter
.\ec20-mode.ps1 -Connect -Pin 1234          # PIN, APN, registration, dial, waits for DHCP, prints the IP
.\ec20-mode.ps1 -Connect -Apn cmnet         # sets the APN on context 1 first
.\ec20-mode.ps1 -Mode mbim                  # checks cxwmbclass and the WWAN interface
.\ec20-mode.ps1 -Mode qmi                   # back to the factory default (-Revert does the same)
```

[`tools/ec20/ec20-mode.sh`](../../tools/ec20/ec20-mode.sh) (Linux, root)
uses the modem port (the third FF/00/00 interface: 03, or 05 in RNDIS mode),
which ModemManager ignores on the TaishanPi in QMI mode:

```sh
sudo ./ec20-mode.sh status
sudo ./ec20-mode.sh rndis   # checks rndis_host is bound afterwards
sudo ./ec20-mode.sh mbim    # checks cdc_mbim
sudo ./ec20-mode.sh qmi     # back, checks qmi_wwan
```

Exit codes for both: 0 done and checked; 1 refused or cancelled; 2 the
read-back did not match; 3 no AT port; 4 the module did not come back;
5 the mode is set but the expected driver is not bound. Windows only:
6 the MBIM driver is bound but the module never answers MBIM OPEN; 7 the SIM
needs a PIN or PUK, or the PIN was refused; 8 not registered; 9 no DHCP
address on the RNDIS adapter.

## Board test plan

Both OSes, in this order, on one SIM. Keep each step's output.

**1. Linux, QMI (baseline).** `sudo tools/ec20/ec20-mode.sh status`:
`usbnet: 0`, interface 4 on `qmi_wwan`. Place one call to a known number and
confirm audio both ways (uplink was never confirmed by a person).

**2. Linux, switch.** `sudo tools/ec20/ec20-mode.sh mbim`. Pass: exit 0,
interface 4 on `cdc_mbim`, ttyUSB0..3 unchanged. Record
`lsusb -v -d 2c7c:0125 | grep -B2 -A8 "Interface Association"` (the IAD
question for Windows) and `AT+QCFG="USBCFG"` on ttyUSB3.

**3. Linux in MBIM mode.** `mmcli -m any`: the modem is found by the
Quectel plugin with an MBIM primary port and a `voice` interface; data
connects through NetworkManager (`nmcli c up` on the cellular connection,
`ping -I wwan0 1.1.1.1`); after registration the voice service logs
"voice over USB audio: ok"; place and receive one call each, audio both
ways. Reboot (cold) and repeat the call: 3 boots. Fail: no voice interface
in MM, or silent calls in MBIM but not in QMI (then see the per-OS options).

**4. Windows.** `.\tools\ec20\ec20-mode.ps1 -Status`: `usbnet: 2`, MI_04 class
02/0E with service `cxwmbclass` and status OK, no separate 0A function.
Settings shows Cellular; `netsh mbn show interfaces` and
`netsh mbn show readyinfo *` show the SIM ready. Connect, then
`ping -S <cellular IP> 1.1.1.1`, browse, a 100 MB download. Toggle airplane
mode off and on; reboot twice: Cellular reconnects without the APN being
re-entered. `regress.ps1`: `devmgr` still PASS (a separate MBIM data
function would show up there as a device with no driver).

**4b. Windows, RNDIS.** With ec20-ports.inf 2.0 installed:
`.\tools\ec20\ec20-mode.ps1 -Mode rndis`, then `-Connect -Pin <PIN>`.
Pass: three usbser ports (MI_03..MI_05), MI_00 on `wceisvista.inf` with a
Remote NDIS adapter, a DHCP address, `ping -S <IP> 1.1.1.1`, a 100 MB
download. Record which port answered AT and the `AT+QNETDEVCTL=?` reply.

**5. Back to Linux after Windows.** Data and a call again: Windows may have
written APN profiles into the module (`AT+CGDCONT?` before and after step 4).

**6. Revert path.** `.\tools\ec20\ec20-mode.ps1 -Revert` on Windows, then
`sudo tools/ec20/ec20-mode.sh status` on Linux: `usbnet: 0`, `qmi_wwan`
bound. Switch to MBIM again for daily use.
